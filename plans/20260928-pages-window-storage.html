Design proposal · Pages · September 28, 2026

Persistent storage for pages, injected on window

Today a page is a read-only broadcast: it can render, sort, and filter what was baked into it, and keep private per-browser state in localStorage, but one reader's click is invisible to everyone else. This proposal adds a small persistent JSON store to every page, exposed to page script as window.superset.storage, held in one Durable Object per page, quota-limited, and live for everyone reading it — turning pages into two-way surfaces the whole org writes to through one link.

TL;DR: extend the runtime script Superset already injects into every page with a window.superset.storage API. The page can't reach the network (CSP is default-src 'none'), so calls travel over postMessage to the host app — which has the viewer's real session — and reach a page.store tRPC router that authorizes the page in Postgres and then calls that page's PageHub Durable Object, where the records live in SQLite. No Postgres table, no migration. Writes are viewer-scoped (you can only overwrite your own records), reads see everyone's, and quotas are enforced at every layer: 8 KiB per value, 128 keys per viewer, 256 KiB per page. No CRDTs needed — one record per viewer means there is nothing to merge, and the hub applies a page's writes one at a time anyway. The hub pushes every change down an open socket, so a tally moves live, and it also gives us human and agent presence for free and retires the heartbeat columns and lease procedures that fake liveness today (section 3). The whole design converges with what claude.ai already ships for artifacts (section 4).

1 · Use cases

Since agents author pages, storage means an agent can ship a tiny working app instead of a document. The use cases fall into three buckets, and the third is the reason to build it.

Collect a signal from the org

each viewer writes their own record · the page derives a view from getAll()

  • Votes and polls — "which design variant?", "which name do we ship?". A design-shotgun comparison board that collects the verdict itself instead of comments trickling in.
  • RSVPs and signups — offsite attendance, on-call swaps, workshop slots.
  • Claiming — a bug-bash or migration checklist where each row has a claim button; a claim is your record on that row's key, so double-claims can't happen.
  • Estimation poker — hidden per-person estimates, revealed when everyone's record is in.
  • Retro boards — each person's cards are their own records; grouping is derived on read.
  • Lightweight approvals — a release-readiness page where each stakeholder stamps ✅/❌ with a note; the page is the sign-off record, versioned like everything else.
  • Onboarding checklists — each new hire checks off their own steps; the author sees who's stuck where.

Remember the reader

each viewer reads their own records back

  • Cross-device continuity — the filter you set on desktop is the filter your phone shows. localStorage only remembers one browser.
  • Read-tracking on recurring pages — a daily digest that collapses what you've already seen.
  • Preferences that survive republishing — storage keys to the page, not the version, so your column sort outlives the agent's nightly republish.

Close the loop back to agents — the headline

humans click · the publishing agent reads structured answers back and acts

Pinned comments already flow back to the watching agent, but they are free text, one thread at a time. Storage gives that channel structure: an agent publishes a triage page listing 40 flaky tests, teammates click fix / ignore / needs owner on each row, and the agent reads the rows back and executes the decisions — no comment parsing, no form service, no separate backend. The same shape covers variant picks, feature-flag ramp approvals, "which PRs land today", and incident action-item assignment.

The page becomes a form the org fills out and an agent executes. That is what no static HTML artifact elsewhere can do, and it makes agents more capable rather than pages merely prettier — so v1's definition of done is this loop (agent-side read of a page's storage ships with viewer-side writes), not the poll.

The common thread: none of these justify standing up a real app, all of them die without shared state, and all fit inside "8 KiB values, JSON, seconds-fresh". The voting page used as the worked example below is just the smallest demo of the first bucket.

2 · Implementation — v0 is built; architecture, API, data model, quotas, rollout

What v0 already does

A working v0 is in the tree, on branch different-ox-a595deff, and it is Durable-Object-only: there is no Postgres table and no migration at all. A page's records live in its PageHub SQLite and nowhere else. What is built: the hub (apps/realtime/src/page-hub.ts) with quota enforcement and change broadcast, two Worker routes (ops behind the shared secret, a subscribe socket behind a ticket), a page.store tRPC router that authorizes the page in Postgres and then calls the hub, the injected window.superset.storage runtime with push-driven subscribe, the host bridge wired in both the web viewer and the desktop pane, and a lunch-vote page to try it on.

There is also a local harness (apps/realtime/scripts/storage-harness.ts) that runs the real runtime and the real hub with only the session layer stubbed, so you pick who you are from a dropdown and two windows are two people. Driving it in a real browser is what caught the head-injection bug below.

Verified against a local Worker, not just typechecked: upsert semantics (changing your vote leaves one row), quota refusal with its code, a wrong secret refused, a live write arriving on a subscriber's socket, a ticket for one page refused on another's stream, and the deletion paths — one person's records dropped across every key while another's survive, re-running the purge cleanly, and a full wipe on page delete.

Deletion is wired: deleting a page wipes its hub, purging an account removes that person's records from every page they wrote on, and org-wide usage is answerable — all three through one pointer table that holds no content (section 3).

Not in v0: the mobile WebView bridge, and the CLI/MCP surface for agent readback — the list procedure exists, but nothing calls it from a terminal yet. One deliberate narrowing from the design below: every procedure is authenticated, so a signed-out viewer of an everyone page cannot read storage either, where the design says anonymous should read but not write.

Why the obvious route is closed

Every page is served on its own origin (https://<pageId>.frame.supersetusercontent.com) by the usercontent Worker under this policy (packages/shared/src/usercontent/csp.ts): 

default-src 'none'
script-src 'self' 'unsafe-inline'
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
img-src 'self' data: blob: https:
…
form-action 'none'

There is no connect-src, so it inherits default-src 'none': fetch, XHR, EventSource, and WebSockets are all blocked from page script. That is deliberate — the file's own docblock says "Network is closed … a page is a document that computes" — and this proposal keeps it. Opening connect-src would turn every published page into a surface that can exfiltrate whatever it computes. We don't touch the CSP at all.

The second closed route is identity at the Worker. Page URLs carry an HMAC ticket that deliberately holds no user id, and rendered HTML is cached per (storageKey, RENDER_REVISION) for 24 hours across all viewers. So the Worker can never answer "whose vote is this", and nothing per-viewer can be baked into the document.

The architecture: brokered through the host

One channel already crosses the sandbox boundary: Superset injects /_superset/runtime.js into every page for comment anchoring, and it speaks postMessage with the host viewer, which validates the frame's exact origin on every message. The host — web app, desktop pane, or mobile WebView — is where the viewer's authenticated session and tRPC client live. Storage rides the same rails:

Each call is a request/response pair with a correlation id:

  1. Page script calls superset.storage.set("vote", "option-b"); the runtime posts { channel: "superset-storage/frame", id, op: "set", key, value } to parent and holds a pending promise keyed by id.
  2. The host's page viewer — the same component that already brokers comment messages — forwards the op to a new page.storage tRPC procedure as the signed-in viewer.
  3. The procedure checks the viewer can read the page, enforces quota, writes the row, and the host posts { channel: "superset-storage/host", id, ok, value } back; the runtime resolves the promise.

The API a page author sees

Everything is JSON in, JSON out. Writes are always scoped to the current viewer; reads can see either your own record or everyone's. That asymmetry makes a voting page trivial and makes vandalism (overwriting someone else's vote) impossible by construction rather than by policy — and it is also why no CRDT or Yjs layer is needed: two people writing at once touch two different rows, so there is nothing to merge. 

const store = window.superset.storage;

await store.ready;                  // false-y if no host is listening (see edge cases)

await store.set("vote", "option-b");    // upsert MY record under this key
const mine = await store.get("vote");   // read MY record back
await store.remove("vote");             // delete MY record

const all = await store.getAll("vote"); // everyone's records for this key:
// [ { user: { id, name }, value: "option-b", updatedAt: "…" }, … ]

store.subscribe("vote", (records) => render(records)); // push over the
// PageHub socket when connected (section 3); focus + 15s polling as the
// automatic fallback — same callback either way

A later revision can add an explicit last-writer-wins shared scope (store.shared.set(…)) for pages that want one mutable document rather than a record per viewer. V1 ships without it: every collaborative shape we actually want first — votes, RSVPs, claims, reactions — is per-viewer records plus getAll.

Data model and quotas

One SQLite table inside each page's hub. No Postgres, so no migration: 

-- inside PageHub(pageId), in Cloudflare
records (
  key         TEXT     NOT NULL,
  user_id     TEXT     NOT NULL,   -- opaque; names resolved by the API
  value       TEXT     NOT NULL,   -- JSON
  size_bytes  INTEGER  NOT NULL,
  updated_at  INTEGER  NOT NULL,
  PRIMARY KEY (key, user_id)       -- one row per viewer per key
)

The primary key is the design: a vote is an upsert of your own row, so changing your mind replaces one row rather than adding a second, and two people voting at once touch two different rows. Storage keys to the page, not the version — the pages skill already promises authors that browser storage persists across versions, and a republished poll should keep its votes. Because the hub is one object per page, it is also the only writer, so the byte and key counts it measures cannot be stale by the time it writes.

Quotas start deliberately small — this is for votes and checklists, not datasets — declared as exported constants and enforced at all three layers — in the page before it calls out, in the API's input schema, and finally in the hub, which is the only thing that can count the page's real total — per the codebase's own rule that "a client is not a gate":

ConstantValueRefused when
MAX_PAGE_STORAGE_VALUE_BYTES 8 KiB a single value's serialized JSON exceeds it
MAX_PAGE_STORAGE_KEYS_PER_USER 128 a viewer's distinct keys on one page exceed it
MAX_PAGE_STORAGE_BYTES 256 KiB the page's total sum(sizeBytes) would exceed it

A refused write comes back as a typed error the page can show ({ ok: false, code: "quota_exceeded" }), not a silent drop. Per-viewer rate limiting is still to do; the hub serializing a page's writes bounds the damage in the meantime.

A new permission shape, named explicitly

Today only a page's creator can write to a page; everyone in the org can read an org page. Storage introduces a genuinely new rule: anyone who can read the page can write their own storage records on it. That is the point — a poll where only the author can vote is not a poll — but it means user-generated content now lives under a page the author didn't write. Two consequences we handle up front:

  • Anonymous viewers are read-only. A visibility: "everyone" page served to a logged-out reader has no user id; getAll works, set returns { ok: false, code: "unauthenticated" }. No anonymous-session identity in v1.
  • The author can see and clear storage. superset pages storage list|clear <page> in the CLI, and takedown/delete of a page cascades its storage rows.

The worked example: a voting page

The entire page-side logic of the poll:

<div id="options"></div>

<script>
  const OPTIONS = ["Tacos", "Ramen", "Pizza"];
  const store = window.superset?.storage;

  async function render() {
    const records = store ? await store.getAll("lunch-vote") : [];
    const mine = store ? await store.get("lunch-vote") : null;
    const tally = Object.fromEntries(OPTIONS.map(o => [o, 0]));
    for (const r of records) tally[r.value] = (tally[r.value] ?? 0) + 1;

    document.getElementById("options").replaceChildren(...OPTIONS.map(o => {
      const b = document.createElement("button");
      b.textContent = `${o} — ${tally[o]}`;
      b.disabled = !store;
      if (mine === o) b.setAttribute("aria-pressed", "true");
      b.onclick = async () => { await store.set("lunch-vote", o); render(); };
      return b;
    }));
  }

  render();
  store?.subscribe("lunch-vote", render);
</script>

One record per viewer means changing your vote is just another set, and the tally is derived on read. No page-side locking, no merge logic, no way to stuff the ballot.

Edge cases the exploration surfaced

  • The thumbnail renderer has no parent frame. Page thumbnails come from Cloudflare Browser Rendering loading the page with no host at all, so parent.postMessage goes nowhere. The runtime resolves store.ready to false after a short handshake timeout and every op then fails fast — a storage-using page must render something sane with zero records, which the voting example above already does.
  • The API has to exist before the page's own script runs. Superset injects the comments runtime before </body>, which is after anything the author wrote — so a page reading window.superset.storage while parsing, which is the obvious way to write one, found nothing there and rendered its empty state forever. The storage runtime is therefore a second script, injected into <head> as a blocking tag (not defer or async, both of which run after inline scripts). The comments runtime stays at the end of the body, where it wants a parsed DOM. This was found by running it in a browser, not by reading it.
  • The colo cache does not key on the runtime's content. RENDER_REVISION hashes the runtime's path plus the theme CSS, not its source, so a runtime change leaves the 24-hour HTML cache untouched — which is what we want, since the document only carries a script tag pointing at that path. The script itself is served max-age=300, so a runtime change reaches published pages within five minutes — a window worth remembering when testing a runtime edit. The revision does hash the script paths, though, so adding the head script above correctly invalidates every cached document.
  • Mobile has its own bridge. The mobile WebView re-posts frame messages through injectedJavaScript; the new channel must be mirrored there or storage silently no-ops on phones.
  • The pages skill becomes wrong. It currently tells agents "nothing else listens to postMessage, so don't build a handshake on it" and that storage is per-browser only. Updating plugins/superset/skills/page/SKILL.md (and republishing the plugin) ships with the feature, so agents start building storage-backed pages the day it lands.

Deliberately out of scope for v1

  • Shared last-writer-wins scope — additive later, and per-viewer records cover the launch use cases.
  • CSP changes and anonymous write identity — both load-bearing invariants with written rationale; neither is needed for the brokered design.

Implementation plan

1

Schema and router

pageStorage table + migration; a page.storage tRPC router with set / get / getAll / remove, quota constants in packages/shared, quota + rate-limit enforcement, cascade on page delete.

2

Runtime and host bridge

Extend the injected runtime with window.superset.storage and the superset-storage/* channels; add the forwarding handler to the shared page viewer component (covers web and desktop at once), with origin validation identical to the comments channel.

3

Realtime: the PageHub Durable Object

A PageHub class beside OrgHub in apps/realtime; the host viewer opens the socket and subscribe switches from the polling timer to push, with human and agent presence riding the same connection. Roughly 2–3 days on top of the polling version because the auth, deploy, and partyserver plumbing already exist. Details in section 3.

4

Agent-side readback, mobile, author tools

superset pages storage list|clear in the CLI and MCP so the publishing agent can read the collected answers — this ships with v1, it is the point. Then superset pages watch as a socket client of the hub, which is also where agent presence comes from. Mirror the channel through the mobile WebView bridge.

5

Docs and the proof

Update the pages skill so agents know the API, and launch with an agent acting on collected answers — a variant-vote page where the agent proceeds with the winner — not just a lunch poll.

6

Retire the watch machinery

Once the hub demonstrably handles the offline-agent case, move watch ownership and the pending-delivery queue into its SQLite and drop watchState, watchHeartbeatAt, and the five lease procedures. A cutover with both paths live, not a delete — comment delivery works today and must not regress.

3 · Realtime with Durable Objects — what a DO is, the PageHub design, presence, and the watch machinery it retires

What a Durable Object is

A Durable Object is a Cloudflare primitive: a tiny single-instance server created on demand, one per name, with its own private storage attached. Four properties matter here:

  • One instance per key, always the same one. Address it by page id and every request for that page, from anywhere in the world, routes to the same instance. "One hub per page" isn't something we build — the platform gives it by construction.
  • Single-threaded on purpose. The instance processes one message at a time, so every write to a page is handled in order. No races, no locks, no "two servers wrote at once — who wins?" The hardest problem in shared state doesn't exist.
  • Durable storage. Each instance carries a private transactional SQLite database that survives hibernation, redeploys, and machine failures. Idle objects cost nothing and wake with state intact. To be explicit, because the name invites the wrong picture: that SQLite lives inside Cloudflare, next to the code that owns it — nothing is stored on a viewer's machine, and it has no relationship to the desktop app's local state. A DO can't run Postgres, so embedded SQLite is what Cloudflare gives each instance instead; OrgHub already uses it.
  • It holds WebSockets. Connected clients stay attached, so when a write commits the object loops over its open sockets and pushes the change. That is the entire realtime story — no pub/sub cluster, no broker.

Together those four are the anatomy of a Firestore-style document store, which is why realtime is cheap here rather than a moonshot. And the substrate already runs in this repo: apps/realtime is a partyserver app whose OrgHub Durable Object (one per organization, SQLite-backed, JWT verified against the API plus an org-membership check) fans out content-free "hosts / cloud workspaces changed" nudges today. Auth, deploy, and plumbing are solved; PageHub is a second small class in the same app, keyed by page id instead of org id.

The PageHub design

page script ── postMessage ──> host viewer ── WebSocket ──> PageHub DO (id = pageId)
   subscribe("vote")             (has JWT)              ▲     ├─ SQLite: live records,
                                                        │     │         watch ownership,
        superset pages watch ── WebSocket ──────────────┘     │         pending deliveries
        (the agent, as a peer)                                ├─ applies each write, in order
                                                              ├─ async write-through → Postgres
                                                              ├─ broadcasts changes to every
                                                              │  connected host and agent
                                                              └─ presence = who is connected

The page still never touches the network — the CSP stays fully closed. The host opens the socket (authenticating with its JWT; the hub checks "can this user read this page" against the API, mirroring OrgHub's membership check), forwards storage ops from the bridge, and relays broadcast changes into the frame. The window.superset.storage API does not change at all: subscribe("vote", cb) fires in ~100 ms instead of ~15 s, and the polling path remains the automatic fallback whenever the socket is down — the same stream-with-polling-floor contract Claude's artifact db documents.

Where the data lives: the hub, and only the hub

The first draft of this proposal kept a Postgres copy and write-through from the hub. We dropped it. One system of record means no dual-write divergence, no reconciliation job, no "which one is authoritative" question later — and no schema change at all, so no migration and no foreign key into the hot auth.users table. The API still fronts every call, because whether a viewer may touch a page is a Postgres question (visibility, author, takedown) that the hub cannot answer. The hub stores opaque user ids; names are resolved by the API on the way out, so renaming someone leaves no stale copy and the hub holds nothing personal.

What that would cost, left alone: every cross-page question. A hub can only answer about itself, so per-page questions stay easy and anything spanning pages becomes impossible — "delete everything this user ever wrote" (their rows sit in N hubs with nothing naming them), "how much storage is in use org-wide", "show me everything from this account" for moderation. Page deletion is the same shape: a foreign key used to cascade for free, and now something has to tell the hub out loud.

Buying those questions back: one pointer table

So we added exactly one table, and it is not a mirror of the records: 

page_storage_index (
  page_id     uuid,
  user_id     uuid,
  updated_at  timestamptz,
  PRIMARY KEY (page_id, user_id)
)   -- no values, no sizes, no content. No foreign keys.

It holds only where to look. Three properties make it carry its weight without reintroducing the dual-write problem we dropped it to avoid:

  • It is deliberately an over-approximation. A row is written on first write and not removed when a single key is deleted, so it means "may have written here" — and a purge that finds an empty hub is a no-op. That keeps the write path to one upsert and makes a stale row harmless rather than wrong.
  • It is best effort. Losing an index write costs a future purge some completeness; it never costs the viewer their vote. Failing a write over a bookkeeping row would be the worse trade.
  • It has no foreign keys, and that is the point. These rows are pointers into storage Postgres cannot see, so a cascade would delete the pointer while leaving the records it was the only way to find. The obvious schema is the broken one.

With it, all three questions come back. Page deletion wipes the hub and forgets the pointers, inside the existing best-effort cleanup — and note the records are already unreachable by then, since every read goes through the API and the page no longer resolves, so this is hygiene rather than containment. Account purge walks the index, asks each named hub to drop that person's rows, then clears the pointers; it runs with the other external deletions and is re-runnable, which matters because the user row is tombstoned rather than deleted, so no cascade would ever have fired. Org-wide usage walks the index and asks each hub its total, capped, and reports when it stopped short rather than passing a partial total off as the whole truth.

Because the hub serializes writes, we get something Firestore itself doesn't guarantee: strict per-page write ordering, with no last-writer-wins ambiguity.

What realtime unlocks that polling can't

  • Live tallies — votes move on everyone's screen as they're cast; the demo becomes two laptops, one link, numbers moving.
  • Presence — who is here, human or agent, which is a big enough consequence to get its own part below.
  • Reveal moments — planning poker where everyone's estimate flips over the instant the last person submits.
  • Meeting-speed surfaces — retro boards and standup pages that work during the meeting, where a 15-second delay would make them unusable.

Presence, and the watch machinery it retires

A hub per page pays for itself twice, because "who is looking at this page right now" is a question we currently answer by simulating liveness in Postgres. Nothing holds a live connection today, so the pages table carries watchState and watchHeartbeatAt columns, and a procedure family — claimWatch, renewWatch, releaseWatch, reserveWatchDelivery, finishWatchDelivery — exists to fake it with heartbeat rows and delivery leases. That is the standard workaround when a database is the only shared state.

With a hub, liveness stops being a simulation and becomes a fact: a session is present if and only if its socket is open, and the hub knows the instant it drops. No heartbeats to renew, no leases to expire, no stale-watcher reaper. Three things follow:

  • Human presence — "7 viewing, 5 voted", live cursors on a retro board, avatars on the page header.
  • Agent presence — the page can show "Claude is listening" as a peer alongside human viewers, and readers know a pinned comment will actually reach someone. Claude's artifact runtime does exactly this: its presence peers carry a kind: "agent" for the publishing session.
  • The CLI becomes a socket client. superset pages watch connects to the page's hub with the same JWT auth OrgHub already uses, and comments and storage events push to the waiting agent instead of being polled for. Connect/disconnect is the whole protocol.

One caution before deleting tables, though: presence and delivery guarantees are different problems. Part of why the lease machinery exists is the offline case — a comment pinned while the watching agent's terminal is closed must survive until something claims it, and presence cannot answer that; only durable state can. So the clean split is:

  • Into the hub's SQLite: watch ownership, the pending-delivery queue, and connection state. It is transactional and survives hibernation, so it is a legitimate home for a queue — and it is the thing the sockets are already talking to.
  • Staying in Postgres: the page itself — identity, visibility, author, versions, takedown — which is what every authorization decision reads, and the only thing that can answer a question spanning more than one page.

Read that way, "clean up the tables we added" lands as: the storage records never get a table in the first place, and the liveness-simulation columns and lease procedures retire once the hub proves it handles the offline-agent case. That is a real simplification of code that exists today, and it is the strongest argument for doing the hub in v1 rather than deferring it.

Honest caveats

  • Each page's writes serialize through one instance in one location — perfect for org-scale collaboration (tens of concurrent writers), not thousands. Pages never need thousands.
  • Retiring the watch machinery is a migration with a cutover, not a delete: comment delivery works today and must not regress, so the hub runs alongside the existing procedures until it demonstrably handles the offline-agent case.
  • Mobile's WebView host needs the socket too (React Native WebSockets are fine, but it's a third bridge to wire).
  • The thumbnail renderer still has no host and no socket — the same graceful zero-records degrade applies.
4 · Prior art: Claude's artifact db — claude.ai already ships this shape; what we take from it

Published claude.ai artifacts get a window.claude API injected by the hosting shell, and await claude.use("db") hands page script a persistent, realtime, Firestore-style document store shared by the artifact's viewers — documents and collections, get/set/ update/delete, filtered queries, and onSnapshot subscriptions with latency compensation. Claude the agent can read and write the same rows from outside the page, so "publish a form, humans fill it, agent reads structured answers and acts" is a shipped loop there today.

The architectures converge

Their design and this proposal make the same three moves, independently: the page is sandboxed with no network of its own; a host-injected runtime bridges calls out (claude.use() there, window.superset.storage here); and identity comes from the signed-in shell, never from the page or its URL. Their realtime contract is also ours: delivery "rides a realtime stream when available and falls back to periodic refresh" — push with a polling floor. That an independent team landed on the same shape is the strongest available evidence the shape is right.

Voting is their canonical example too

Their access rules are declarative, fixed at publish, keyed on sharing level, and their own documentation uses exactly the per-viewer-record shape this proposal hardcodes: 

db: { rules: [
  { path: "votes", read: "view", write: "owner" },   // everyone reads
  { path: "votes/{self}", write: "interact" },       // each writes only their own
]}

Our v1 is that rule as the only mode. If we ever generalize, their rules syntax is the blessed path — no need to invent one.

Rules of theirs worth adopting from day one

  • "Can't see" equals "doesn't exist". They have deliberately no permission-denied and no not-found on reads: a document a viewer cannot see behaves identically to one that was never written. Kills a whole class of probing.
  • Named-quota errors. Every cap rejects with a stable code and a message naming which cap (quota_exceeded, resource_exhausted) so pages can tell viewers what happened instead of failing silently.
  • No transactions, and say so. They ship last-writer-wins plus one cooperative TTL-lease primitive, and shape the data model (per-viewer paths, derive-on-read) so conflicts don't arise. Same call here.
  • Private-from-the-owner subtrees. Their per-viewer paths are hidden even from the artifact's owner, which enables sealed votes and planning poker (write privately, copy to a shared path when you reveal). Worth keeping in mind for our v2.

What we deliberately don't copy in v1

Queries, subscriptions-with-64-cap, leases, nested collections, and the rules engine are three years of surface area serving use cases we don't have yet. Our flat per-viewer-record API is the ~10% that serves every launch use case, with their contract as the map for wherever we grow next. Competitively this also frames the stakes: Superset's pitch for pages over artifacts is "the org's surface — listed, versioned, comments wired to agents." Interactivity is now a dimension where artifacts are ahead; this proposal closes it.
